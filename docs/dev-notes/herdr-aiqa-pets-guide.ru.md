# herdr для AIQA и PETS: практический разбор

## TL;DR

`herdr` - это terminal-native multiplexer для одновременной работы с несколькими coding-агентами в одном интерфейсе: workspaces, tabs, panes, статусы агентов, персистентные сессии и локальный API для оркестрации.

Главная ценность не в "ещё одном терминале", а в управлении параллельными агентами как системой:

- видно, где агент `blocked`, `working`, `done`, `idle`;
- можно отсоединиться (`detach`) и вернуться позже без потери процессов;
- можно оркестрировать работу через CLI/socket API (split, run, wait, read);
- можно масштабировать QA-поток без ручного хаоса переключений между окнами.

Ключевое ограничение для твоего текущего режима: официальный `herdr` рассчитан на Linux/macOS. В Windows-only режиме без WSL/SSH прямой запуск как основной инструмент сейчас нецелесообразен.

Для AIQA/PETS `herdr` особенно полезен, когда нужно параллельно вести:

- impact analysis;
- подготовку task package;
- тесты/ретесты;
- проверку change gate;
- triage и сбор evidence.

## Что такое herdr и какую проблему решает

Когда в работе один агент, достаточно обычного терминала или чата. Когда агентов несколько (например, один гоняет тесты, другой готовит документацию, третий собирает impact), возникают типовые проблемы:

- контекст размазывается по вкладкам/окнам;
- непонятно, где ждать вмешательства;
- много ручной координации;
- высокий риск пропустить готовый результат или блокировку.

`herdr` решает это как "слой диспетчеризации" поверх терминала:

- не заменяет терминал веб-дашбордом;
- показывает реальное terminal output;
- добавляет status awareness и контроль параллельных потоков.

## Как устроен herdr

## Confirmed

- Единицы организации: `workspace -> tab -> pane`.
- По умолчанию используется persistent session server: клиент можно detach/reattach, а процессы продолжают работать.
- Состояния агента: `blocked`, `working`, `done`, `idle` (и `unknown` как техническое состояние API).
- Доступны встроенные интеграции (в README/INTEGRATIONS): `pi`, `claude`, `codex`, `opencode`.
- Есть гибридная модель определения состояния:
  - process detection отвечает за владение pane/liveness;
  - hooks/plugins дают семантические состояния, где доступны;
  - heuristics по экрану остаются fallback.
- Есть локальный socket API + CLI wrappers для оркестрации:
  - создание/focus/rename/close workspace/tab/pane;
  - split pane;
  - run/send input;
  - read pane output;
  - wait по output и wait по `agent-status`.

## Практический смысл этих механизмов

- **Workspaces**: изолируют задачи по репозиториям/эпикам.
- **Tabs**: разделяют контексты внутри задачи (например, `analysis`, `tests`, `logs`, `notes`).
- **Panes**: параллельные исполняемые потоки (агент, тест-раннер, tail логов, утилиты).
- **Persistent sessions**: агент продолжает работу без "держать терминал открытым".
- **Agent awareness**: фокус внимания на очереди вмешательств, а не на постоянном ручном опросе каждого окна.

## Ограничения и риски

## Confirmed

- В официальной установке указано требование Linux/macOS.
- Лицензия проекта: AGPL-3.0.
- По умолчанию логи пишутся локально в `~/.config/herdr/`.
- Интеграции улучшают качество статусов, но не все агенты имеют одинаково богатую hook surface.

## Assumption

- Для командного применения потребуется согласовать policy по доступу к рабочим терминалам/логам и формат хранения артефактов.

## Risk

- В Windows-only без WSL/SSH запуск `herdr` как штатного инструмента создаст friction вместо ускорения.
- При reliance только на heuristics (без интеграций) возможно меньше точности статусов на граничных кейсах.
- При отсутствии дисциплины task package можно собрать много execution-шума без роста auditability.

## Что это дает именно в AIQA (`D:\DevReps\aiqa`)

AIQA задает четкие границы:

- canonical truth в `aiqa/`;
- adapters не являются source of truth;
- task artifacts важны как evidence, но не автоматически каноничны;
- killer feature: cross-repo legacy impact reasoning, а не просто diff listing.

`herdr` хорошо ложится на этот подход как execution-слой:

1) **Параллельные потоки без смешения ролей**
- отдельная pane/tab на каждый независимый поток;
- orchestration-owner сохраняется (соответствует `parallel-execution.md`).

2) **Impact reasoning как рабочий конвейер, а не один чат**
- одна pane: diff + impact map;
- вторая: проверка `required_checks`;
- третья: сбор task evidence.

3) **Честность maturity**
- можно явно разделять planned vs executed: то, что реально запускалось, фиксируется в отдельных потоках и читается из output.

4) **Поддержка metric-friendly дисциплины**
- проще собирать данные по coverage/checklist/runbook-исполнению из структурированных потоков выполнения, а не из несвязанных чат-логов.

## Что это дает в PETS (текущий проект)

В PETS есть жесткая дисциплина change gate:

- обновление `tasks/` под материалные изменения;
- сверка путей с `repo-index.yaml`;
- `scripts/check_change_gate.py`;
- тесты (включая e2e) до интеграции.

`herdr` здесь полезен как "операционный пульт":

### Пример раскладки под QA change gate

- `pane A`: `git status`, `git diff`, `git diff <base>...HEAD`.
- `pane B`: обновление task-файла и Committed change record.
- `pane C`: `python scripts/check_change_gate.py --staged` и без `--staged`.
- `pane D`: pytest/e2e запуск.
- `pane E`: triage/logs.

Результат: меньше контекстных потерь и лучше воспроизводимость перед commit/push.

## Почему это лучше обычных чатов для такой работы

Чаты хорошо подходят для обсуждений и единичных запросов. Для параллельного QA/dev исполнения у них системные ограничения.

Преимущества `herdr` относительно "чат + ручной терминал":

1) **Персистентность исполнения**
- процессы продолжают жить после detach;
- нет необходимости держать одну сессию/вкладку "живой" ради выполнения.

2) **Наблюдаемость состояния**
- видно, кто blocked/done/working;
- не нужно циклически "пинговать" каждого агента вручную.

3) **Реальный source of truth**
- работа опирается на прямой terminal output, а не на пересказ в чате.

4) **Оркестрация через API**
- можно автоматизировать wait/read/send/split сценарии;
- чаты обычно требуют человека как ручного маршрутизатора.

5) **Аудит и повторяемость**
- проще воссоздать исполнение по панелям и командам;
- меньше "скрытых шагов", сделанных вне видимости.

## Windows-only вывод для твоего текущего режима

## Confirmed

- В режиме "только Windows, без WSL/SSH" `herdr` не является практичным штатным решением прямо сейчас.

## Рекомендация

Использовать сейчас эквивалент дисциплины без `herdr`:

- фиксированная схема panes/tabs в Windows Terminal;
- строгий runbook: отдельные вкладки под diff/gate/tests/tasks;
- обязательная фиксация evidence в task package;
- единый owner для финальной консолидации.

Если появится WSL2 или Linux-host, запускать ограниченный пилот `herdr`.

## Пилот внедрения (когда будет Linux/WSL2)

1. Выбрать 1 типовую задачу с change gate + тестами.
2. Завести workspace на задачу и стандартизировать 4-5 pane ролей.
3. Подключить доступные интеграции (`claude`/`codex` и т.д.).
4. Прогнать 3-5 задач с одинаковым workflow.
5. Сравнить против baseline:
   - время до готового change gate;
   - число пропущенных шагов;
   - доля задач с полным evidence;
   - субъективная нагрузка на переключение контекста.

## Критерии, когда herdr окупается

- параллельно работают 2+ агента/процесса;
- есть повторяемый QA/dev pipeline;
- важна наблюдаемость "кто ждёт вмешательства";
- есть потребность в воспроизводимом audit trail;
- есть Linux/WSL2 среда для штатной эксплуатации.

Если работа в основном "один агент + один поток + короткие задачи", выигрыш будет меньше.
